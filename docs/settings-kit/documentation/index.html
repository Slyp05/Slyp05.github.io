Settings Kit v1.0.0

Namespace

All public Settings Kit types are in the SettingsKit namespace. Add this at the top of your scripts to access them: 

using SettingsKit;

How It Works

Settings Kit lets you declare Project Settings and Preferences pages, read their values anywhere, including at runtime in a built player, without writing editor boilerplate and without putting anything under Assets/Resources/.

You write one small page class and one or more serializable entry classes. From that alone, the settings automatically appear in the right window (Project Settings or Preferences), are stored in the right place (ProjectSettings/ or UserSettings/), ship into builds when appropriate, and are read through a tiny static API.

There is no registration step and no Resources/ folder. Entry types are discovered automatically in the editor: each is stored once, kept in sync as you add or remove types, and (for build settings) injected into the build so a player can read the same values.

Settings Kit is aimed primarily at package makers who need configuration: add it as a dependency, declare a page, and your settings surface in the editor and travel with the build. It works just as well for a single project that wants clean, version-control friendly settings.

A small surface by design. Settings Kit deliberately exposes only a handful of types, so there is little to learn and your settings code stays stable as the package grows.

Kinds of Settings

Which base class an entry inherits decides where it appears, how it is stored, and whether it ships into the build. There are four:

SettingsEntry<TPage> Build setting. Project Settings window, stored in ProjectSettings/SettingsKit.asset, ships into the build and is readable at runtime.
PlatformSettingsEntry<TPage> Per-platform build setting. Like SettingsEntry<TPage>, but its values can differ per build target.
EditorSettingsEntry<TPage> Editor-project setting. Project Settings window, stored in ProjectSettings/SettingsKit.asset, but never shipped into a build.
UserSettingsEntry<TPage> Per-developer setting. Preferences window, stored in UserSettings/SettingsKit.asset, never shipped.
Where to declare them. Editor-project and user settings never ship, so in a build Settings.Get returns their type defaults. Put them in an Editor assembly, or, for convenience, in your Runtime assembly (gating with #if UNITY_EDITOR if they use editor-only types).

Quick Start

Three steps: declare a page, declare settings on it, read them anywhere.

using SettingsKit;
using UnityEngine;

// 1. Declare a page (once).
public sealed class MyGamePage : SettingsPage
{
    public override string Path => "My Game";              // shown under Project Settings > My Game
    public override string Description => "Runtime tunables for My Game.";
}

// 2. Declare settings on that page.
[System.Serializable]
public sealed class AudioDefaults : SettingsEntry<MyGamePage>
{
    [SerializeField, Range(0f, 1f)] float masterVolume = 0.8f;
    public float MasterVolume => masterVolume;
}

// 3. Read them anywhere, including at runtime in a built player.
float volume = Settings.Get<AudioDefaults>().MasterVolume;

That is the whole loop: the page appears in Project Settings, and the value ships into the build.

Declaring a Page

A page is the tree node that groups your settings. Declare it once by inheriting SettingsPage. It shows in Project Settings, in Preferences, or both, depending on the entries attached to it: build and editor-project entries appear under Project Settings, user entries under Preferences. 

public sealed class MyGamePage : SettingsPage
{
    public override string Path => "My Game";                 // required; "/" nests, e.g. "My Game/Networking"
    public override string Description => "Runtime tunables.";   // optional; help box at the top of the page
    public override string HelpUrl => "https://docs.example.com";  // optional; draws a "?" button
}

The tree label and the page's ordering among its siblings come from an optional [SettingsDisplay] attribute (the same one used for entry sections). Without it, the label is the last segment of Path and the order is zero.

A page is identified by its type, not its title, so two packages that each declare a page named "Settings" get separate pages. Entries sharing the same page type land on the same page.

Path is read once per editor session and cached, so it must be constant. Description and HelpUrl are read each time the page is drawn, so they may be computed.

Declaring Settings

A settings entry is a serializable class bound to a page through one of four base types. The base you inherit decides its kind.

Every concrete entry must:

  • be marked [System.Serializable],
  • have a parameterless constructor (the implicit one is fine),
  • expose its data with [SerializeField] fields.

A field's initializer, or your constructor, sets its default, which is also what a per-entry reset restores.

Version control. Unity's standard .gitignore tracks ProjectSettings/ but ignores UserSettings/. So build and editor-project settings (ProjectSettings/SettingsKit.asset) are committed and shared with the whole team, while user settings (UserSettings/SettingsKit.asset) stay per-developer. Keep it that way.

Build Settings

SettingsEntry<TPage> is the default kind: committed, shipped into the build, and readable at runtime, with the same value on every platform. 

[System.Serializable]
[SettingsDisplay("Audio", Order = 0)]
public sealed class AudioDefaults : SettingsEntry<MyGamePage>
{
    [SerializeField, Range(0f, 1f)] float masterVolume = 0.8f;
    public float MasterVolume => masterVolume;
}

A build entry can also reference project assets (a Texture2D, a Material, a ScriptableObject, ...). Because the shipped container is a real asset, those references are pulled into the build and loaded at runtime alongside it.

Per-Platform Settings

PlatformSettingsEntry<TPage> is a build entry whose whole set of values can differ per build target. You mark the entry as per-platform and read plain fields; the system resolves them to the right platform. 

[System.Serializable]
[SettingsDisplay("Backend", Order = 10)]
public sealed class BackendConfig : PlatformSettingsEntry<MyGamePage>
{
    [SerializeField] string apiUrl = "https://api.mygame.com";   // plain field, no per-platform wrapper
    public string ApiUrl => apiUrl;
}

In the editor, the section gains a tab strip for adding per-platform values. Entering Play previews the active build target's values.

At build time, each per-platform entry is baked to the target's values, so a player carries only its own platform's data.

For values that are the same on every platform, use an ordinary SettingsEntry<TPage> instead.

Editor-Project Settings

EditorSettingsEntry<TPage> is edited under Project Settings, but never shipped. Use it for team tooling configuration. 

[System.Serializable]
[SettingsDisplay("Asset Pipeline")]
public sealed class ToolingSettings : EditorSettingsEntry<ToolingPage>
{
    [SerializeField] string exportFolder = "Exports";
    public string ExportFolder => exportFolder;
}

User Settings

UserSettingsEntry<TPage> is per-developer and local, edited under Preferences. 

public sealed class PreferencesPage : SettingsPage
{
    public override string Path => "My Game";   // shown under Preferences > My Game
}

[System.Serializable]
[SettingsDisplay("Editor Comfort")]
public sealed class UserPreferences : UserSettingsEntry<PreferencesPage>
{
    [SerializeField] Color highlight = Color.cyan;
    public Color Highlight => highlight;
}

A page is not tied to one window. Attach a user entry and it appears in Preferences; attach a build or editor-project entry to the same page and it also appears in Project Settings, each window showing only its own entries.

Reading Settings

Read any entry through the static Settings facade.

float volume = Settings.Get<AudioDefaults>().MasterVolume;
string url = Settings.Get<BackendConfig>().ApiUrl;   // resolves to the running platform

Get<T>() returns your settings; a per-platform entry resolves to the running platform.

At runtime, treat what you read as read-only: any changes you make to it are not saved. To change values, edit them in the settings window, or from editor code (see below).

Waiting for load in a player

In the editor, Settings.Loaded is always true. In a player it is false only during startup, before the preloaded container the build ships has enabled, which happens before the first scene loads. While false, Get<T>() answers with default values.

When the check is needed. The container enables before the first scene, so from the first scene's Awake onward a read is always safe: any scene MonoBehaviour (Awake / OnEnable / Start) and RuntimeInitializeLoadType.AfterSceneLoad never observe false. Only code that can run before the first scene needs to gate on Settings.Loaded: an early [RuntimeInitializeOnLoadMethod] (AfterAssembliesLoaded, BeforeSplashScreen, or BeforeSceneLoad), a static constructor, or a field initializer.

When it is needed, gate the read: 

if (Settings.Loaded)
    Apply(Settings.Get<AudioDefaults>());
// else retry later; the value would otherwise be a default, not the configured one

Saving edits made from editor code

Settings.Save() persists changes made from editor tooling. It is editor-only and stripped from builds, so it is always safe to call.

Sections & Ordering

Each entry appears as a section on its page, headed by the nicified type name (AudioDefaults becomes "Audio Defaults"). Use [SettingsDisplay] to set an explicit title, a tooltip, and an order. 

[SettingsDisplay("Audio", Tooltip = "Master mix defaults.", Order = 0)]
public sealed class AudioDefaults : SettingsEntry<MyGamePage> { /* ... */ }

The same [SettingsDisplay] attribute sets a page's tree label and order. Sections within a page are ordered by (Order, type name), lower first, and pages among their siblings by their own order.

Sections whose value differs from the declared default are marked with a thin neutral-grey accent bar on the left, and offer a right-click Revert that resets the entry to a fresh default.

Custom Rendering

By default an entry's fields are drawn flat under its section header. To customize how a section looks, write an ordinary PropertyDrawer targeting your settings type, exactly as you would for any serializable class. 

[CustomPropertyDrawer(typeof(NetworkConfig))]
public sealed class NetworkConfigDrawer : PropertyDrawer
{
    public override float GetPropertyHeight(SerializedProperty property, GUIContent label)
        => EditorGUIUtility.singleLineHeight;

    public override void OnGUI(Rect position, SerializedProperty property, GUIContent label)
    {
        SerializedProperty host = property.FindPropertyRelative("host");
        SerializedProperty port = property.FindPropertyRelative("port");
        // ... draw host and port on one line ...
    }
}

Validation

Implement IValidatedSettings on any entry to validate it. The single hook is used in two places: an inline help box in the settings window, and, for a build entry, a build-time gate. 

[System.Serializable]
[SettingsDisplay("Networking")]
public sealed class NetworkConfig : SettingsEntry<MyGamePage>, IValidatedSettings
{
    [SerializeField] int port = 7777;

    public bool Validate(out string error)
    {
        if (port < 1024 || port > 65535)
        {
            error = $"Port must be between 1024 and 65535 (was {port}).";
            return false;
        }

        error = null;
        return true;
    }
}

In the settings window, a failing entry draws its message as a help box under the section: error-styled (red) for a build entry, since it will block a build, and warning-styled (yellow) for editor-project and user entries.

At build time, the injector calls the same Validate on each build entry, collects every failure, and throws a single BuildFailedException naming the offending page and section.

Migration

Two opt-in hooks let a package evolve its own settings across releases without losing a consumer's stored data. Both run in the editor only, when the settings load; a player reads already-migrated, baked data, so there is no runtime migration cost.

Pure field renames and type moves are handled by Unity's own [FormerlySerializedAs] and [MovedFrom] attributes; use those first. The hooks below cover what those cannot: transforming values, and rescuing data from a deleted type.

Versioned same-type migration

Implement IVersionedSettings to transform an entry's already-deserialized fields forward, gated by a version stamp. Bump Version whenever the stored shape changes; Settings Kit records the version each entry was saved at and calls Migrate once per upgrade step. 

[System.Serializable]
public sealed class AudioDefaults : SettingsEntry<MyGamePage>, IVersionedSettings
{
    [SerializeField, Range(0f, 1f)] float masterVolume = 0.8f;

    // Kept only so version 1 data (volume was stored 0..100) can migrate forward.
    [SerializeField, HideInInspector] int legacyVolume0To100 = -1;

    public int Version => 2;

    public void Migrate(int fromVersion)
    {
        if (fromVersion < 2 && legacyVolume0To100 >= 0)
        {
            masterVolume = Mathf.Clamp01(legacyVolume0To100 / 100f);
            legacyVolume0To100 = -1;
        }
    }
}

The version gate guarantees each step runs exactly once. Cumulative if (fromVersion < n) steps cover multi-release upgrades. For a per-platform entry, Migrate runs on every variant.

Cross-type rescue

When an entry type is deleted outright, its stored data is orphaned. Implement ISettingsMigrator anywhere to recover that data into surviving types before the orphan is cleared. Each discovered migrator is offered every orphaned record; it recognizes its own old type by identity. 

public sealed class LegacySettingsMigrator : ISettingsMigrator
{
    [System.Serializable]
    struct OldNetworkSettings   // mirrors only the deleted NetworkSettings fields we want to recover (need not be all of them)
    {
        public string address;
        public int portNumber;
    }

    public void OnMissing(MissingSettings missing)
    {
        // Match the deleted type by its original name (a plain string, since the type no longer exists to nameof),
        // and its namespace and assembly, taken from a surviving sibling.
        if (missing.ClassName != "NetworkSettings"
            || missing.Namespace != typeof(NetworkConfig).Namespace
            || missing.AssemblyName != typeof(NetworkConfig).Assembly.GetName().Name)
            return;

        if (missing.TryRead(out OldNetworkSettings old) == false)
            return;

        // Write the recovered values into a surviving entry, then persist.
        NetworkConfig current = Settings.Get<NetworkConfig>();
        // ... copy old.address / old.portNumber into current ...
        Settings.Save();
    }
}

MissingSettings exposes the deleted type's class, namespace, and assembly names, plus TryRead<TOld>, which parses the stored serialized data into a mirror type you declare. The mirror only needs the fields you want to recover, not every field the original had; any it leaves out are simply ignored. Each orphan is offered once, then cleared, so the rescue is not repeated.

Navigation

Settings.OpenPage<TPage>() focuses a page in its window (Project Settings or Preferences), so you can add a button in your own tooling that jumps straight to your settings. It is editor-only and stripped from builds. 

[MenuItem("Tools/My Game/Open Settings")]
static void Open() => Settings.OpenPage<MyGamePage>();

Testing

Settings.OverrideForTests<T>() returns a disposable that substitutes what Get<T>() returns for the life of the handle, so you can unit-test code that reads settings without touching the stored file. The override reverts automatically on dispose. 

[Test]
public void UsesConfiguredVolume()
{
    AudioDefaults stub = new() { /* set up a test instance */ };

    using (Settings.OverrideForTests(stub))
    {
        // code under test reads Settings.Get<AudioDefaults>() and sees the stub
    }
    // substitution is reverted here
}

Because the seam is scoped and reverting, there are no permanent "for tests" setters leaking into the shipped API.

Build & Shipping

You do not configure anything for a build; shipping is automatic. During a build, an editor hook injects a temporary copy of the project container into the player's preloaded assets, containing only build entries. Editor-project entries and the user container are excluded, so editor-only types never reach the build.

  • Object references ship too. Because the injected container is a real asset, any project assets a build entry references are pulled into the build and loaded at runtime alongside it.
  • Per-platform entries are baked to the target's resolved values, so a player carries only its own platform's data.
  • Validation gates the build: a failing build entry throws a BuildFailedException naming the page and section.
  • The injected copy is temporary: it is stripped and deleted after the build, and a leftover from a crashed build is swept up automatically.
