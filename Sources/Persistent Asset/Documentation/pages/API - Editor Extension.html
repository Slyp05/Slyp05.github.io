PersistenceManagerEditor

EditorextendingPersistentAsset.Editor

Base editor giving a custom PersistenceManager the standard inspector (Problems, Serializer, Parameters, Actions, Status, Save Data). Inherit it with a [CustomEditor] and override a Draw* hook; call base to keep the standard content. Worked example: A custom inspector.

Public
void DrawAsChild()Draw what a composite manager's row has to show about the manager it owns: what is wrong with it, and nothing else. Give the row a button selecting that manager, so its settings are edited in its own inspector. Its settings are deliberately not drawn in the row: a section inside a row indents twice over and shares its folded state with the owner's section of the same name.

ManagerComposition

staticextending2.0PersistentAsset.Editor

Authoring support for a manager made of other managers (see Platform (Routing)). An owned manager is a hidden sub-asset of the same object and never runs on its own: its owner drives its storage. One level deep, and an owned manager nothing references is swept away. Worked example: A manager whose storage is other managers.

Wrap every change a composite manager's editor makes in this: one of them touches its own routing, a child asset and the names carrying the order, and an undo landing between two of those leaves a part pointing at nothing, or a manager nothing references that the project then reports as leftover garbage.

AssetRegistration

staticPersistentAsset.Editor

The editor side of AssetRegistry: it decides which assets save data may point at, and keeps the table the runtime reads in sync with the project. Use it to register assets from your own editor tooling. See Save asset references.

string Register(Object asset)Registers an asset and returns its id (null when it cannot be registered, such as a scene object). Idempotent.
void Unregister(string id)Unregisters an id. Saved references to it stop resolving.
string RegisterForTool(Object asset, string owner = null)Registers an asset your own tooling maintains, so the same tooling can take the entry back later. A manual entry is left as it is. One a registered folder or a reference produced is claimed, so the pass that recomputes those cannot take the registration away. owner names the tooling making the claim: pass a constant of your own, and the same one to UnregisterForTool, so an asset two tools need survives the first taking its claim back. Naming none claims the entry under the unnamed owner, which every call naming none shares.
void UnregisterForTool(Object asset, string owner = null)Takes back the claim RegisterForTool made under the same owner. Includes one it claimed from a registered folder or a reference, which the next refresh re-derives. The entry goes with the last claim on it, so an asset other tooling still claims stays registered. Another tool's claim is not one of yours to remove, and an entry the user added by hand is left alone.
IDisposable Batch()Groups registrations so the settings file is written once at the end instead of once each. Wrap a run of them in using. IsRegistered is not authoritative inside a batch, since the table it reads is only rebuilt when the batch closes.
string ComputeId(Object asset)The id an asset would be registered under (its GUID, plus the local file id for a sub-asset), without registering it.
Object Resolve(string id)The asset an id points at, for display: the registry answers first, then the project, so an asset that lost its registration still shows.

ManagerSetup

static2.0PersistentAsset.Editor

Acting on Persistence Manager assets from an editor script. A manager lives as a sub-asset of the object it answers for, which these take care of. Composites are ManagerComposition.

SettingsTestScope

sealed2.0PersistentAsset.Editor

Sends every settings read and write to a throwaway container for the life of the scope, so an EditMode fixture of your own registers assets and locks managers without the project's settings file ever holding what it did, not even when the editor crashes part way through a run. One scope stands at a time: opening another ends the one already open, so a fixture whose teardown never ran leaves nothing for the next one to inherit.

new SettingsTestScope()Opens a scope whose settings start out empty. Open it in the fixture's setup, or wrap a run of tests in using.
void Dispose()Ends the scope: everything written into it goes, and the project's own settings answer again.
